# 游戏开发代码审查与实现规划

审查代码改动是否遵守项目架构与约定，输出审查报告，并规划下一步实现。**只读操作，代码修改交回 impl-developer。**

## 执行流程

1. 读取 `README.md` 掌握架构分层与约定。
2. 确定审查范围（用户指定的文件 / commit；未指定则审查最近功能改动的相关文件）。
3. 按 `references/review-checklist.md` 逐项审查，重点核查架构合规（见下文）。
4. 对照 `docs/prd/` 的验收标准与 `tests/` 用例，标注未覆盖项。
5. 输出报告到 `docs/review/<YYYYMMDD>-<对象>.md`，问题分级：严重（必须修）/ 建议（应该修）/ 可选。
6. 报告末尾输出下一步实现规划，作为后续开发周期输入。

## 架构合规（一票否决项）

以项目 README 的分层说明为准（未定义时按典型四层），通用要求：

| 层 | 合规要求 |
|---|---|
| 数据层 Data | 静态常量 + 纯函数；不持有可变状态 |
| 逻辑层 Logic | 规则引擎零引擎节点依赖；禁止 `extends Node`、`add_child`、`await get_tree()`、`get_node()`、访问场景树 |
| 胶水层 Glue | 事件携带完整数据；状态迁移有明确定义 |
| 表现层 Presentation | 只消费事件队列与状态机，**不做规则判定**；不在表现层出现数值 / 步数 / 判定逻辑 |

## 测试覆盖评估

- 规则改动是否先跑了 headless 回归再进表现层；
- 新功能是否有对应用例（正常路径 + 边界条件，对照项目 PRD 的玩法规则逐条检查）；
- 随机性是否用固定 seed / 指定骰值保证断言确定性；
- 测试脚本是否都在 `tests/` 目录。

## 下一步规划输出规范

每条规划必须完整呈现（做什么 / 为什么 / 怎么改），不能只给摘要表格：

- **P-01 <标题>**
  - 做什么：目标与范围；
  - 为什么：来源（本次审查发现 / PRD 待办 / 技术债）；
  - 怎么改：涉及文件、分层、预估改动量；
  - 优先级与依赖：P0/P1/P2，依赖哪条规划先行。

## 输出要求

- 报告：`docs/review/<YYYYMMDD>-<对象>.md`；
- 回复中完整呈现报告与规划全文，供用户决策。
