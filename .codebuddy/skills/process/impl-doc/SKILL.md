# 游戏开发实现文档与测试用例

根据已确认的 PRD 子需求，编写实现设计文档并补充测试用例，随后编码实现并通过 headless 回归。

## 执行流程

1. 读取 `docs/prd/` 下对应 PRD，认领 1~2 条子需求（按优先级与依赖顺序）。
2. 按 `references/impl-doc-template.md` 生成 `docs/design/<特性名>.md`。
3. **测试先行**：先在 `tests/` 下写测试用例（此时可失败），再实现代码让其通过。
4. 分层实现顺序：数据层（BoardData）→ 逻辑层（GameRules）→ headless 验证 → 胶水层（事件 / 状态机）→ 表现层。
5. 每层完成后跑对应验证命令，全部通过后输出改动清单与测试结果。

## 架构硬约束

以项目 README 的架构分层为准（未定义时按以下典型分层），核心要求各层职责不可越界：

- 逻辑层（规则引擎，如 `game_rules.gd`）：`extends RefCounted`（或引擎等价的非节点类），零节点依赖。禁止 `extends Node`、`add_child`、`await get_tree()`、访问场景树或 `get_node()`。
- 数据层（如 `board_data.gd`）：静态常量 + 纯函数（static func），不持有可变状态。
- 表现层：只消费事件队列与阶段状态机，**不自行做规则判定**；规则判定结果全部由逻辑层产出事件。
- 事件命名：动宾结构（示例：`pawn_moved`、`card_played`、`turn_advanced`），事件携带完整数据（玩家 / 实体 / 起止位置），表现层无需回查规则。

## 测试用例设计

测试脚本放 `tests/` 目录，命名 `<功能>_test.gd`（或扩展 `sim_game.gd` / `click_smoke.gd`）。用例必须覆盖：

1. **正常路径**：规则的最基本情况（如掷 6 起飞）。
2. **边界条件**（对照当前项目 PRD 的玩法规则逐条检查，通用检查维度）：
   - 核心规则的正常触发与不触发条件；
   - 连锁 / 叠加情形（连续效果、多实体同格、规则交叉时的判定优先级）；
   - 终局结算（数值越界处理、精确终止、胜利 / 失败判定）；
   - 特殊回合机制（额外行动、跳过、次数上限——若规则定义）；
   - 多玩家 / 多实体轮转顺序与边界。
3. **随机性处理**：测试中不依赖真实随机——用可注入的伪随机源（seed 固定或直接指定骰值），保证断言确定性；需要统计分布时批量跑 N 局（N ≥ 100）。
4. **断言输出**：每条用例输出 通过 / 失败 与失败详情；脚本退出码非 0 表示存在失败（供命令行判断）。

## 命令速查（Windows / PowerShell，Godot 项目示例）

| 用途 | 命令 |
|---|---|
| 逻辑回归 | `godot --headless --path . --script res://tests/<回归脚本>.gd` |
| UI 冒烟 | `godot --headless --path . --script res://tests/<冒烟脚本>.gd` |
| API 探测 | `godot --headless --path . --script res://tests/<探测脚本>.gd` |

> 具体脚本名与启动命令以当前项目 README 的命令速查为准；非 Godot 项目按其引擎对应的无头命令替换。

## 修改纪律

- 最小化改动：read_file → replace_in_file 定向修改，禁止整文件重写；
- 不删改与本子需求无关的代码；
- 临时诊断代码必须打标（如 `# DIAG:` 前缀），便于集成阶段验证通过后统一清理。
