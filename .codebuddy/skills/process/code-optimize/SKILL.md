# 存量代码质量与逻辑设计优化审查

对现有代码做整体质量审查：可读性、坏味道、逻辑设计、架构健康度，
产出可决策的重构/优化方案。**只读操作；方案未经用户确认禁止改任何代码。**

## 与 game-dev-code-review 的分工

| | game-dev-code-review | 本技能（code-optimize-review） |
|---|---|---|
| 对象 | 本次功能**改动** | 存量代码**整体** |
| 视角 | 合规（分层/测试/约定） | 质量（可读性/设计/坏味道） |
| 时机 | 阶段④ | 随时，尤其用户主观觉得"丑"时 |

## 执行流程

1. 读 `AGENTS.md` 与 `README.md`，掌握架构硬约束与分层约定（一票否决项不得违反）。
2. 确定审查范围：用户指定的文件/模块；未指定时按模块逐个过（core → presentation → autoload）。
3. 按 `references/smell-checklist.md` 逐项检查，每发现一处记录：位置（文件:行）、问题描述、严重度。
4. 对每处问题尝试映射设计模式/惯用法，参照 `docs/specs/godot-design-patterns.md`
   （状态/命令/策略/观察者/组件等在 Godot 下的落地方式）；
   该文档不存在时按通用《Game Programming Patterns》知识给出建议。
5. 产出优化方案到 `docs/review/<YYYYMMDD>-optimize-<范围>.md`，按输出规范列 O-xx 条目。
6. 在回复中完整呈报方案全文，**停下等用户确认**；确认后：
   - 纯重构（不改玩法行为）：先跑 `run_tests.bat` 留存基线，确认全绿后才动代码，改完复跑回归；
   - 涉及玩法数值/判定条件：回灌 `docs/prd/requirements.md`，从阶段① PRD 重新启动。

## 审查维度（按序检查）

1. **分层合规**：core 是否纯净（零节点依赖）、presentation 是否只消费事件不做判定、autoload 是否只放薄全局状态。
2. **可读性**：命名、函数长度、嵌套深度、魔法数字、重复代码。
3. **逻辑设计**：状态机是否显式、动作合法性检查与执行是否分离、事件数据是否自足、随机性是否可注入。
4. **Godot 惯用法**：信号边界（向上/向下）、硬路径、上帝节点、场景自包含、组合 vs 继承。
5. **优化机会**：哪些位置可用状态/命令/策略/观察者模式显著简化（只建议高收益项，不为模式而模式）。

## 优化方案输出规范

每条必须完整呈现（做什么/为什么/怎么改/风险），不能只给摘要表格：

- **O-01 <标题>**
  - 位置：`文件路径`（含行号范围）
  - 问题：现状与坏味道描述（引用代码片段）
  - 怎么改：目标结构与关键改动点，涉及哪些文件/层
  - 为什么：收益（可读性/可测性/扩展性）
  - 风险：可能的回归点、需要的测试护栏
  - 优先级：P0（影响正确性/可维护性根基）/ P1（明显收益）/ P2（锦上添花）
  - 改动量：小（<50 行）/ 中 / 大

方案末尾给出建议的执行批次（同批次内条目互相独立、可单独回归）。

## 纪律

- 只读审查，不改代码、不改测试。
- 方案必须可执行：每条都有明确文件与结构描述，不留"考虑优化一下"式空话。
- 重构必须有回归护栏：没有测试覆盖的模块，方案中先补测试条目再列重构条目。
- 高收益优先：不为套模式而重构，无明确收益的"美化"不列条目。
