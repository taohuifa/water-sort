# 代码可学习性优化（code-learnability）

把"能跑但难读"的代码，重构为"新人能顺着读下去"的代码。
**铁律：只改结构与注释，不改业务行为**——重构前后程序行为必须完全等价。

## 执行流程

1. **通读目标代码**，用一句话概括它"整体做什么"；说不出来就先问用户或查文档，禁止脑补业务语义。
2. **列职责清单**：把代码块逐段标注"这段在干什么"，同一函数里出现 ≥2 个互不相关的"干什么"，就是拆分点。
3. **按 `references/refactoring-playbook.md` 的手法重构**：拆函数（一个函数一个用途）→ 抽公共逻辑复用 → 分离编排与实现 → 补教学式注释。
4. **验证行为等价**：有测试跑测试（单测/回归）；没有测试时，重构前先补最小冒烟验证再动代码，禁止无验证交付。
5. **输出对照讲解**：给用户看 before/after 对照（见输出规范），让"为什么这样改"看得见。

## 重构硬约束（一票否决）

- **行为等价**：不改输入输出、不改副作用时序、不改异常路径语义。拿不准就不改。
- **最小改动**：先 `read_file` 再 `replace_in_file` 定向修改；不整文件重写，不顺手改无关内容。
- **测试先行**：重构前必须确认有可运行的验证手段（现有测试或临时冒烟脚本，后者验证通过后清理）。
- **命名即文档**：函数名要能回答"干什么"，达到"读名字就懂、读注释就通"。
- **遵守项目分层**：目标项目的架构约束（分层/依赖方向/命名规范）优先于本 skill 手法。

## 输出规范

- 重构后每个函数满足：**一个用途、5~10 行主体、一句话能说清**；函数总长（含 docstring）
  **硬上限 50 行**，超线必须拆（5~10 行是"段"的节奏，50 行是"函数"的红线）。
- 注释写法固定两槽位：行尾标 `# 操作：这行在做什么`，关键行标 `# 结果：得到什么/为什么`。
- 函数用途写在**自己 docstring 首行**（讲解语气，可带 ①②③ 分步），不在文件头堆速查表、
  不用"为什么…？因为…"问答式（详见手法手册 §4.1 反模式）。
- 交付时给 **before/after 对照**（各 ≤15 行的关键片段）+ 一段话说明改了什么、为什么更易学。
- 改动较大时，先给重构方案（拆分清单 + 复用关系图）等用户确认，再动代码。

## 讲解规范（重构后带用户读代码时的纪律）

- **先钉死术语再讲流程**：领域术语先给一句话定义，并明确"它不是什么"——用户会按
  生活语义理解术语（实测：把"策略 policy"理解成"一次下注动作"，实际它是被训练的
  网络本身），术语没对齐前讲流程必然反复。
- **区分两个维度**：**数据组织单位**（手/行，数据怎么分组）≠ **被修改对象**
  （策略网络，训练改的是谁）。这两个维度混淆是新手最常见的卡点，讲解时显式拆开说。
- **类比先行**：抽象流程先给生活类比（如"考试刷题"：考试=手、题目=决策行、
  批改=功劳分配、学生=策略网络），再映射回代码实体。
- **收束给一句话版本**：讲完给一句可背诵的总结（如"AI 用自己的打法打牌 → 每步
  下注记成账 → 用输赢打分 → 按分数修改打法"），并回答用户的原始是非问（是/否
  要先说，再展开）。
